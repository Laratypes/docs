# Frontend client

`@laratype/client` turns the API object into a typed fetch client. The frontend calls endpoints by name, and the request and response types come from the contracts, the same ones the server uses.

The frontend imports only `app/contracts/index.ts` (`appApi` and `AppApi`), never anything from the server's routes (see [Contracts › The API object](./contracts#the-api-object)). The client package depends only on `@laratype/contract`, has no Node dependencies and leaves the schema library to you. The frontend needs TypeScript 5.4 or later.

The design was decided in the S2 spike ([#85](https://github.com/Laratypes/Laratype/issues/85)). On `master` the package is still an empty scaffold, so everything on this page is planned.

::: info Illustrative example
The examples follow the design notes and the S2 spike reference shapes in the [client spec](https://github.com/Laratypes/Laratype/blob/master/docs/v1/client.md). None of this code runs today, and names may change. They use the `users` contract from [Controllers](./controllers).
:::

## Creating a client <Status issue="109" />

`createClient(appApi, options)` takes the API object itself, so there is no build step:

```ts
// frontend/api.ts
import { createClient } from '@laratype/client' // package per #109, not final
import { appApi } from '../app/contracts'

export const api = createClient(appApi, { baseUrl: '/api' })
```

Each endpoint becomes a method under its route name:

```ts
const user = await api.users.show({ params: { user: '1' } })
const page = await api.users.index({ query: { page: 2 } })
```

- The input object has `params`, `query` and `body` as the endpoint needs them, plus optional `headers` and `signal`.
- The input is optional when nothing in it is required.
- The client fills in the path with encoded params, serializes the query and sends the body as JSON.
- The contract's schemas reach the browser too, so a form can validate with the same schemas as the server.

The client and the server's `route()` helper are meant to share one URL builder in `@laratype/contract` ([#162](https://github.com/Laratypes/Laratype/issues/162), see [Contracts › Building URLs](./contracts#building-urls)).

Keep the frontend's `tsconfig` separate from the app's. The app config loads Hono's JSX types, which would pull server types into the frontend program. The frontend config uses `types: []` and the DOM library ([#109](https://github.com/Laratypes/Laratype/issues/109)).

A frontend in a separate repository cannot import `appApi`. It uses a file generated by `sauf types:generate` instead ([#133](https://github.com/Laratypes/Laratype/issues/133)), which the type generation guide will cover. The client and contract runtime is meant to stay under 5 kB gzip, not counting the schema library ([#132](https://github.com/Laratypes/Laratype/issues/132)).

## The result union <Status issue="110" />

A call resolves to a result that you narrow by `ok` and then by `status`:

- `{ ok: true, status, data }`, where `data` has the response type;
- `{ ok: false, status, error }` for each error the endpoint declares, where `error` has that error's body type;
- a variant for network errors and statuses the contract doesn't declare.

`users.store` declares `errors.validation`, so a failed call can be a 422 with the validation body. Assuming `CreateUser` has `name` and `email`:

```ts
const res = await api.users.store({ body: { name: 'Ada', email: 'ada@example.com' } })

if (res.ok) {
  res.data // UserDto, status 201
} else if ('unexpected' in res) {
  // a status the contract does not declare
} else if (res.status === 422) {
  res.error.errors // { [field]: string[] }
}
```

The `'unexpected' in res` check comes first because the undeclared-status variant has `status: number`, which also matches `422`. Until it is ruled out, `res.status === 422` cannot narrow `error` to the validation body. The S2 spike marks that variant with `unexpected: true`; the final shape, and the shape of the network-error variant, come with [#110](https://github.com/Laratypes/Laratype/issues/110).

The type of `data` is still open. It is the response schema's output, but JSON turns some values into others, such as a `Date` into a `string` ([#110](https://github.com/Laratypes/Laratype/issues/110), [#107](https://github.com/Laratypes/Laratype/issues/107)).

## Options and hooks <Status issue="124" />

The planned options of `createClient` are:

- `baseUrl`;
- headers, which can be a function, for example to add an auth token on every request;
- `onRequest` and `onResponse` hooks;
- `credentials`;
- an `AbortSignal`;
- a custom `fetch`.

Their exact names and signatures are not settled yet ([#124](https://github.com/Laratypes/Laratype/issues/124)).

## Path-style calls <Status issue="140" />

A second call style uses the method and the path:

```ts
const user = await api.get('/users/:user', { params: { user: '1' } })
```

- It is type-only. It needs no contract runtime, and the API type comes from `import type` (`ApiTypes<AppApi>`) or from generated types.
- The S2 spike measured it at 0.63 KiB gzip.
- It adds to the named style, which stays the main one.

Here `api` stands for a path-style client. How one is created is not specified yet ([#140](https://github.com/Laratypes/Laratype/issues/140)).

## TanStack Query <Status issue="141" />

`@laratype/client-query` adapts the client to TanStack Query, with adapters for Vue and React, generated query keys and mutations with typed errors. The `examples/fullstack-vue` app will use it ([#136](https://github.com/Laratypes/Laratype/issues/136)).

## Response validation in development <Status issue="159" />

During development the client can optionally validate responses against the contract, to catch drift between the server and the contract. This needs the schemas in the browser, so it only works with `createClient(appApi)` and not with a generated file.
